## Purpose

DevOS holds credentials it did not issue and cannot replace: an organisation's model provider
keys, repository tokens, deployment credentials, and database connections, held so that the
[Plugin System](/architecture/plugin-system) can reach external systems on that organisation's
behalf.

The obligation is therefore stricter than for data DevOS owns. A leaked artefact is a
disclosure; a leaked credential is a capability handed to whoever holds it, usable against
systems DevOS does not operate.

## The constitutional requirement

> **ES-7.** Credentials, tokens, and private keys MUST NOT appear in source control, logs, error
> messages, audit events, generated artefacts, or agent context.
>
> A committed secret MUST be rotated before any other remediation. Removing a secret from a file
> without rotating it MUST NOT be treated as a fix.

Both halves carry weight. The first enumerates six places a secret must never be, and that list
is unusually specific because each is a place secrets routinely end up. The second states the
remediation order, and it is the half most often got wrong.

## Where credentials may exist

**Custody sits with the Plugin System.** Provider credentials are held there and resolved at
call time. No other component holds one.

The consequences are stated across the architecture and are worth collecting:

| Component | Credential access |
| --- | --- |
| Plugin System | Holds credentials; resolves them at call time |
| AI Connect | **None.** Obtains model access as a plugin capability |
| Engines | **None.** Do not construct provider calls |
| Agents | **None.** A contract containing a credential is non-conforming |
| Product surface | **None.** |

Two of these are load-bearing rather than incidental. AI Connect holding no credentials is why
an agent cannot exfiltrate one through its output. Engines holding none is why a bug in an
engine cannot leak one.

**Registration and installation are separate acts** for exactly this reason. A plugin is
registered once, platform-wide, without credentials; it is installed per organisation *with*
that organisation's configuration and credentials. Registration is a platform act; installation
is an organisation act, and the credential belongs to the latter.

## Where credentials may never appear

ES-7's six locations, with what each means in DevOS:

| Location | What this rules out |
| --- | --- |
| **Source control** | No credential in this repository or any project repository, including history |
| **Logs** | No credential in application logs — ES-10 observability output included |
| **Error messages** | No credential in a failure surfaced to a user, an operator, or a caller |
| **Audit events** | Stated again by the Plugin System: no event contains a credential value |
| **Generated artefacts** | No credential in a brief, recommendation, decision record, blueprint, or build unit |
| **Agent context** | No credential in a prompt envelope, result envelope, or execution record |

Four more follow from the architecture rather than from ES-7 directly:

- **Framework definitions.** A framework describes architecture, not a stack; configuration
  values and credential material MUST NOT appear in one.
- **Library assets.** An asset containing a credential value fails the
  [publication gate](/library/asset-standard).
- **Templates.** A [configuration template](/library/templates) carries placeholder keys with no
  values. This is where the risk concentrates, because configuration is copied without being
  read.
- **Build unit prompts.** A prompt reaches an execution worker; a credential in one has been
  handed to whatever runs it.

## Rotation before remediation

A committed secret is compromised from the moment it is committed. Deleting the line does not
un-commit it: the value remains in history, in clones, in caches, in build logs, and in
anything that mirrored the repository.

**Rotation comes first.** Removing the secret, rewriting history, and adding a scanner are all
legitimate follow-ups and none of them changes the fact that the old value still works until it
is revoked.

Treating removal as the fix is explicitly called out as insufficient by ES-7, which is unusual
for a constitutional standard and reflects how commonly it happens.

Rotation is a **human-only** action in supervised agentic work: secret rotation or disclosure is
in the band an agent MUST NOT autonomously perform — see
[Agentic Build Control](/product/agentic-build-control).

## Access

From the [permission matrix](/product/permissions):

| Capability | Owner | Admin | Contributor | Viewer |
| --- | --- | --- | --- | --- |
| Create API credential | Yes | Yes | No | No |
| Revoke or rotate API credential | Yes | Yes | No | No |

A credential's scope cannot exceed the capabilities of the member who created it, and cannot
include write capabilities while the API is read-only — invariant 5 in
[Access control](/security/access-control).

That invariant is what stops credential creation becoming a privilege-escalation path: an Admin
cannot mint a credential that does what only an Owner may do.

## Secrets in agentic development

An execution worker frequently *needs* credentials to do its job — to clone a repository, run a
test suite, or call an API. This is where the boundary between capability and authority is
sharpest.

Three rules hold, each already stated elsewhere:

1. **A worker's access to a credential is not authority to use it for anything else.** Capability
   does not confer authority — see [Access control](/security/access-control).
2. **Secret rotation or disclosure is human-only.** An agent may not rotate a secret, and may not
   disclose one, regardless of what it can technically reach.
3. **Credentials never enter agent context.** A worker may operate in an environment where a
   credential is available to a process; the credential does not travel in the prompt envelope,
   the result envelope, or the execution record.

Rule 3 is a real distinction rather than a technicality. An environment variable read by a test
process is not the same as a value placed into a model's context, because the second is
retained, transmitted to a provider, and potentially reproduced in output.

<Note>
**Not specified.** How execution environments receive the credentials they legitimately need —
injection, short-lived tokens, delegated access, or something else — is not specified by any
current page. The requirement is that the credential does not enter agent context or any of
ES-7's six locations. The delivery mechanism is implementation-defined.
</Note>

## Reusable versus operational

| Reusable — Library asset, Git-canonical | Operational, never in Git |
| --- | --- |
| This standard and the requirements it states | Credential values |
| A secret-rotation [process](/library/processes) | Which credentials an organisation holds |
| A secret-handling [skill](/library/skills) | Installation configuration |
| A configuration [template](/library/templates) with placeholder keys | Rotation history and audit records |

The template row is the one worth care. A placeholder that reads like a real value survives into
production because nobody noticed it was a placeholder; placeholders must be visually obvious
and, where a validation step exists, detectable by it.

## Frameworks may add, never relax

A [Framework](/frameworks/overview) may impose stricter obligations — key custody requirements,
rotation cadences, or separation-of-duties constraints on who may hold what. A
[Fintech](/frameworks/fintech) project is the obvious case.

Frameworks add; they never weaken the baseline. ES-7 applies in full regardless of Framework.

## Acceptance criteria

- No engine, agent, or AI Connect component holds a provider credential, verified by test.
- No credential value appears in any log, error message, audit event, artefact, or agent context.
- No credential appears in this repository or any published Library asset.
- A credential's scope never exceeds its creating member's role.
- Secret rotation cannot be performed by an agent.
- A committed secret triggers rotation before any other remediation.
